# MSc subject-fit guidance

## Contents

- Subject-specific anchors and false positives (1–19, Appendix A)
- Minimum-work and evidence discipline

Treat the following as advisory evidence-reading guidance. Do not add its examples to the atom denominator. An anchor must be substantive enough to support MSc-level discussion of assumptions, alternatives and limitations, not just a keyword match.

## Subject-specific anchors and false positives

| # | Subject | Natural thesis evidence | Reject superficial links |
| --- | --- | --- | --- |
| 1 | Design and analysis of algorithms | A thesis-specific optimization or computation with a justified paradigm, recurrence, correctness argument, approximation bound or randomized guarantee. Benchmark results can support, but do not replace, the argument. | Calling a library sort, indexing a database or using a fast framework does not establish algorithm design. Keep separate from Topic 11's network optimization. |
| 2 | Theory of programming | A relational specification, derived preconditions, meaningful invariant, termination argument, program derivation or verified parallel algorithm tied to the thesis goal. | Test success is not a correctness proof. An informal list of requirements is not a relational specification. Do not infer Owicki–Gries from ordinary threads. |
| 3 | Project Management | Explicit methodology selection, a dependency-aware plan, delivery artifacts or a reasoned project-management practice that affects actual work. Show constraints and consequences. | A solo project's calendar or a claim to be agile is insufficient. Do not pretend to have a team. Framework names in a generic methodology chapter are not evidence. |
| 4 | Formal semantics | A defined thesis language/DSL with operational or denotational rules, a semantic theorem, equivalence argument or inspectable mechanization. | JSON schemas, API descriptions and general mathematical prose are not automatically language semantics. Distinguish this subject from program-correctness Topic 2. |
| 5 | Software quality and testing | Requirements-to-test traceability, justified design techniques, coverage interpretation, a risk-based strategy or static review/analysis with recorded findings. Explain what the evidence cannot establish. | A large test count, CI badge or passing demo alone is insufficient. Do not infer an unspecified ISTQB or ISO edition; use the applicable course version. |
| 6 | Design of Distributed System | A formal problem model with safety/progress obligations, verified component composition, resource-sharing or channel/pipeline reasoning in the actual design. | A microservice deployment, retries or Kafka usage alone does not establish this formal-design course. Keep separate from Petri-net/process-algebra Topic 16. |
| 7 | Advanced Java programming | Student-designed generic abstractions, concurrency contracts, reflective mechanisms, persistence boundaries or another advanced Java mechanism with precise reasoning and evidence. | Being written in Java or using Spring annotations is not enough. The bundled older description is a provisional scope, not proof of the current syllabus. |
| 8 | Introduction to Data Science | A data-analysis process with diagnosed data quality, justified preparation, descriptive mining, model validation or recommendation evidence. | Merely storing or visualizing data is not data science. Distinguish pipeline/evaluation concepts from learner mechanisms in Topic 14 and estimation mathematics in Topic 18. |
| 9 | Models of Computation | A computational model used to formulate a thesis problem, with expressive-power, resource-complexity or representation-size reasoning and a nontrivial application. | Deployment nodes are not automatically a parallel computational model. An application's state diagram need not establish automata-theoretic analysis. |
| 10 | Principles of artificial intelligence | A problem representation and search strategy with heuristic assumptions, search behavior, game reasoning or introductory learning evidence. | Calling a hosted AI API does not establish search or learning theory. Use the September 2025 revision; do not substitute the more mathematical Topic 18. |
| 11 | Advanced Algorithms | A flow, cut, matching or related reduction, algorithm and certificate/bound used to solve the real thesis problem. Discuss feasibility and limits. | A graph database or an architecture diagram is not a network-optimization argument. Keep separate from Topic 1's general paradigms. |
| 12 | Complex information systems | Requirements, UML or process/data models of a real information system; enterprise workflow, access control or integration reasoning tied to concrete organizational needs. | A CRUD application does not establish ERP/logistics/supply-chain knowledge. Grant only the actual linked domains; do not count every enterprise area. |
| 13 | Functional Languages | Inspectable Haskell-specific type/function structures used substantially in the thesis, with explanation of their role and tradeoffs. | Java lambdas, Python comprehensions or an incidental map call do not establish this Haskell course. A cross-language conceptual link needs exact correspondence and supervisor scrutiny, not automatic C. |
| 14 | Machine Learning | A learner's mechanism, hyperparameters and tuning, alternatives and validation tied to a real research question or engineering objective. | A pretrained model call or an unexplained accuracy number does not establish model understanding. No training run means no completed experimental result. |
| 15 | Service Science | A service-system/value model, design/innovation process, semantic description, service analytics/optimization, markets, co-creation or service-level evidence. | An HTTP endpoint is not a service-science argument. Use the revised scope including opportunities and risks of service AI; do not narrow this to web programming. |
| 16 | Analysis of distributed systems | A Petri-net or process-algebra model with meaningful property analysis, transformations, reachability/liveness reasoning or traceable tool results. | Sequence diagrams or concurrent deployment alone do not establish formal analysis. State assumptions and abstraction limitations; do not turn bounded checking into an unbounded theorem. |
| 17 | Introduction to Computer Security | Thesis-specific assets, threats and risks connected to justified controls and safe, authorized verification. | HTTPS or login alone is insufficient. Do not request attacks against third-party systems or expose confidential data. Prefer local fixtures and approved environments. |
| 18 | Methods and tools for AI applications | A mathematical/statistical model with inspectable estimation, optimization, latent-variable or representation reasoning linked to the actual method and results. | Generic AI motivation or library defaults do not establish likelihood/Bayesian/EM mathematics. Keep distinct from Topics 8, 10 and 14. |
| 19 | Scalable enterprise applications | Substantial multi-tier, transaction, invocation/message, lookup or cross-cutting design with explicit state, failure and capacity implications. | Containers and replicas alone are insufficient. Historical Java EE/applets/Jini examples are not recommended modern tools or extra atoms; explain enduring concepts and actual assigned technologies. |
| A / 20 | Advanced Software Technology | An actual MVP, justified execution process, maintainable architecture or innovation assessment can support relationship evidence. | Strong fit never resolves missing selection eligibility. Keep separate from Project Management and outside default recommendations until current-form/faculty confirmation. |

## Minimum-work and evidence discipline

For each failed subject, identify the smallest useful action already justified by the thesis. Name the resulting artifact and what it must show. Possible outputs include an ADR comparing alternatives, a formal specification, a targeted test-design table, a reproducible experiment, an algorithm certificate or a service-value analysis. Do not automatically recommend all of these to every thesis.

If the necessary work is unrelated to the actual goal, say **Do not choose this topic on the present scope**. Suggestions are not evidence; retain N until a grounded plan supports P and retain P until completion supports C. Do not add a topic just because it is easy to study or has a small denominator.
