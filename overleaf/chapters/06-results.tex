\section{Evidence Inventory and Provenance Ledger}

In accordance with empirical systems software engineering standards, this chapter documents directly measured observations, event logs, operating system telemetry streams, and descriptive distributions without speculative interpretation. All performance metrics adhere to the \textbf{Dual-Window Reporting Mandate} (\texttt{CLM-METH-02}), reporting side-by-side:
\begin{enumerate}
  \item \textbf{Whole-Run Metrics ($t \in [0\text{ s}, 55\text{ s}]$):} Full execution window, encompassing client ramp-up and ramp-down ($55.0\text{ s}$ denominator).
  \item \textbf{Steady-State Hold-Window Metrics ($t \in [15\text{ s}, 45\text{ s}]$):} Filtered execution window, isolating the 30-second constant-concurrency hold stage ($30.0\text{ s}$ denominator).
\end{enumerate}

\subsection{Key RQ1 Empirical Invariants}
\begin{enumerate}
  \item \textbf{Monitor Pinning Invariant (\texttt{CLM-RQ1-01}):} In every synchronized trial, JFR recorded exactly \textbf{108} qualifying \texttt{jdk.VirtualThreadPinned} events, matching completed HTTP transactions 1:1.
  \item \textbf{Suppression of Pinning via \texttt{ReentrantLock}}\\ (\texttt{CLM-RQ1-03}): Replacing \texttt{synchronized} with \texttt{ReentrantLock} reduced qualifying pinning events from 108 to strictly \textbf{0}.
  \item \textbf{Throughput Invariance Across Mutex Implementations (\texttt{CLM-RQ1-04}):} Steady-state throughput remained identical at \textbf{$1.967\text{ req/s}$} for \texttt{synchronized} versus \textbf{$1.956\text{ req/s}$} for \texttt{reentrant-lock} (a minor delta of $0.011\text{ req/s}$ or $0.56\%$). Both match the single-server Amdahl ceiling ($\mu = 1/0.500\text{ s} = 2.0\text{ req/s}$).
  \item \textbf{The Ramp-Up Distortion (\texttt{CLM-METH-02}):} In \texttt{platform-synchronized}, whole-run median latency was $3\,917.56\text{ ms}$, whereas steady-state hold median latency was $4\,929.49\text{ ms}$. Incorporating the uncrowded 15-second ramp-up artificially depressed median latency by \textbf{$1\,011.93\text{ ms}$ ($-20.53\%$ relative to the steady-state baseline)}:
  \begin{equation}
    \frac{3\,917.56\text{ ms} - 4\,929.49\text{ ms}}{4\,929.49\text{ ms}} = -20.53\%.
  \end{equation}
  \item \textbf{Diagnostic Upper Bound (\texttt{no-lock}):} Eliminating mutual exclusion increased throughput from $1.967\text{ req/s}$ to \textbf{$16.489\text{ req/s}$} and reduced median latency to \textbf{$506.61\text{ ms}$}.
\end{enumerate}

The empirical findings establish that blocking POSIX system calls silently capture the carrier thread: throughput collapses to \textbf{$1.967\text{ req/s}$} with \textbf{exactly 0 qualifying JFR pinning events ($\ge 20\text{ ms}$)}, while process CPU consumption remains negligible at \textbf{$1.04\% \pm 0.12\%$} (consistent with kernel sleep without user-space spinning). For \texttt{native-short}, the Interactive Response Time Law sets an upper bound on throughput:
\begin{equation}
  X \le \frac{N}{R + Z} = \frac{10}{0.0011\text{ s} + 0.100\text{ s}} \approx 98.9\text{ req/s},
\end{equation}
which is consistent with the empirical steady-state measurement of $76.05\text{ req/s}$ (correcting the preliminary draft artifact of $1\,143.9\text{ req/s}$ which inadvertently calculated inverted service time rather than closed-loop system throughput). In \texttt{pure-java-sleep}, 10 concurrent VUs executing managed \texttt{Thread.sleep(500ms)} achieve $13.00\text{ req/s}$ ($714$ total transactions, $p50 = 505.23\text{ ms}$), demonstrating that managed yields permit carrier reuse whereas native blocking locks the carrier thread in kernel wait.

\section{Historical Baselines and Flawed Strata (Strata 5 and 7)}

In Stratum~5 (historical 8-carrier baseline on Apple M1), unconstrained execution confirmed that \texttt{synchronized} generated 110 pinning events and achieved $1.967\text{ req/s}$, while \texttt{reentrant-lock} generated 0 pinning events and achieved $1.967\text{ req/s}$.
