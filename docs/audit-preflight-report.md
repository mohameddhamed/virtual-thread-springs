However, replacing `synchronized` with `ReentrantLock` unpins carrier threads but **cannot increase throughput** when the critical section is an application-level serialization bottleneck ($\mu = 1/D = 2.0\text{ req/s}$). Unpinning only benefits throughput when carrier threads are the primary bottleneck constraining independent, parallel tasks. Furthermore, OpenJDK 24 (JEP 491) unpins monitors at runtime (0 pins), confirming that monitor pinning is a temporary Java 21 runtime constraint, whereas serialization is an immutable software architecture constraint.
* **RQ2 Closure (Architectural Boundaries & Migration Risks):** **CLOSED.**
  * *Evidence:* Stratum 3 (27 runs), Stratum 4 (18 runs), Stratum 8 (6 runs); `CLM-RQ2-01` through `CLM-RQ2-07`.
  * *Definitive Answer:* Engineering teams must evaluate four critical architectural boundaries before enabling virtual threads:
    1. *Foreign Function Interfaces (JNI/Panama):* Native blocking syscalls (`nanosleep`) hold carrier threads captive in Darwin kernel wait states with ~1% CPU and **zero JFR pinning events**, completely evading JVM pinning telemetry.
    2. *Relational Persistence (HikariCP):* Virtual threads unmount cleanly during connection waits (0 pins), but queue accumulation shifts downstream into the connection pool. Under active connection holding (Stratum 8), throughput is strictly bounded by Little's Law ($X_{\text{max}} = K / T_{\text{hold}}$), collapsing Pool 1 to $3.27\text{ req/s}$ with 49 pending threads while Pool 10 scales tenfold to $32.60\text{ req/s}$.
    3. *ThreadLocal Lifecycles:* Unbounded request context accumulation scales linearly with concurrent virtual threads, threatening heap inflation unless guarded by `finally` blocks or Scoped Values (JEP 506).
    4. *Observability Tools:* Legacy `ThreadMXBean` monitors ignore virtual threads, and default JFR thresholds miss sub-20ms pins, creating telemetry blind spots.

## 13. Defense Rehearsal Checklist & Anticipated Examiner Probes

| Defense Domain | Anticipated Examiner Probe | Evidence-Backed Counter-Argument & Thesis Citation |
|---|---|---|
| **Amdahl Saturation vs. Unpinning** | *"If `ReentrantLock` completely eliminates carrier thread pinning, why does system throughput fail to improve by even 1%?"* | **Answer:** By Amdahl's Law (1967) and queueing theory, the 500 ms critical section in `PaymentService` enforces a single-server service capacity ceiling ($\mu = 1/D = 2.000\text{ req/s}$). Refactoring to `ReentrantLock` unpins the carrier thread, enabling the carrier to execute *other, unrelated* tasks, but cannot parallelize the sequential execution of the critical section itself ([`CLM-RQ1-04`](file:///Users/mohamedhamed/Documents/virtual-thread-springs/docs/evidence-freeze/claim-evidence-ledger.md#L86-L98); Chapter 6, §6.1.1). |
| **Scheduler Constraint Validity** | *"Why did you evaluate your primary matrix under `-Djdk.virtualThreadScheduler.parallelism=1`? Does that not distort realistic server behavior?"* | **Answer:** Single-carrier parallelism is a deliberate **mechanism-isolation boundary**, not an operational sizing recommendation. With one carrier, a pinned virtual thread starves all runnable virtual threads, making monitor pinning deterministically observable without multi-carrier masking. The thesis explicitly contrasts this against an unconstrained 8-carrier baseline in Stratum 5 and rejects calling it a "container CPU quota" ([`CLM-METH-01`](file:///Users/mohamedhamed/Documents/virtual-thread-springs/docs/evidence-freeze/claim-evidence-ledger.md#L265-L276); Chapter 1, §1.4.2; Chapter 3, §3.9). |
| **Silent JNI Carrier Captivity** | *"Why does JFR report zero pinning events during native `nanosleep()` system calls if the carrier thread is blocked?"* | **Answer:** JFR `jdk.VirtualThreadPinned` events are instrumented strictly within HotSpot's Java continuation freeze subsystem (`continuationFreeze.cpp`). When entering native C via JNI, the thread transitions to `_thread_in_native` without invoking `Continuation.yield()`. The OS carrier thread sleeps in the Darwin kernel wait queue, consuming negligible CPU (~1.0%) while remaining occupied, completely evading JVM-level pinning monitors ([`CLM-RQ2-01`](file:///Users/mohamedhamed/Documents/virtual-thread-springs/docs/evidence-freeze/claim-evidence-ledger.md#L148-L160); Chapter 6, §6.2.1). |
| **Relevance Post-JEP 491** | *"Since Java 24 delivers JEP 491 (unpinning object monitors), why is a study on Java 21 relevant?"* | **Answer:** Java 21 is a Long-Term Support (LTS) release supported through 2031 with dominant enterprise adoption (40–68% in 2025/2026 surveys). More importantly, JEP 491 resolves only *runtime schedulability* (Tier 1); it does not solve *application-level serialization* (Tier 2), JNI carrier captivity, or database connection pool exhaustion (Tier 3). Our Java 24 comparative benchmarks (Stratum 2) prove that while pinning drops to 0 on JDK 24, throughput remains strictly serialized at $\approx 1.97\text{ req/s}$ ([`CLM-RQ1-06`](file:///Users/mohamedhamed/Documents/virtual-thread-springs/docs/evidence-freeze/claim-evidence-ledger.md#L114-L126); Chapter 1, §1.1.4; Chapter 6, §6.1.4). |
| **Database Pool Sizing with Loom** | *"Why not simply increase HikariCP connection pool size to 5,000 to match virtual thread concurrency?"* | **Answer:** Database connections are backed by heavy backend server processes, buffer pools, and disk I/O. As demonstrated in Stratum 8, virtual threads shift queueing from the web tier to the database pool. Expanding connection pools beyond the database server's physical CPU/spindle capacity induces severe PostgreSQL lock thrashing and memory exhaustion. Pool sizing must be calibrated by Little's Law and bounded by application-level semaphores ([`CLM-RQ2-03`](file:///Users/mohamedhamed/Documents/virtual-thread-springs/docs/evidence-freeze/claim-evidence-ledger.md#L179-L192); Chapter 7, §7.3.3). |
| **Workload Generation Model** | *"Why did you use a closed-loop k6 workload rather than an open-loop Poisson arrival model?"* | **Answer:** In closed-loop testing ($N = 10\text{ VUs}, Z = 0.100\text{ s}$), client arrivals self-throttle under server queueing, stabilizing system equilibrium and allowing direct mathematical verification of Little's Law ($N = X(R + Z)$).
