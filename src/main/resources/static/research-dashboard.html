Primary Java 21 study

Synchronization

Three repeated trials compare monitor serialization, ReentrantLock, a no-lock diagnostic upper bound, and a platform-thread control under a one-carrier stress condition.

Established

Java 21 synchronized trials produced measured jdk.VirtualThreadPinned events. ReentrantLock and no-lock trials reported zero events.

Not established

Replacing synchronized with ReentrantLock did not remove the application-level serialization or prove a throughput advantage.

Boundary extension

JNI Boundary

Repeated process-level runs keep the Java-21-targeted artifact and one-carrier scheduler fixed while varying runtime and native condition.

Measured

Blocking JNI completed roughly one sixth as many requests as pure Java sleep across Java 21, 24 and 25.

Explicit zero

All 27 JFR recordings report zero jdk.VirtualThreadPinned events for the JNI matrix.

Interpretation layer

Mechanism Explorer conceptual

01

Monitor pinning

In the Java 21 treatment, blocking while holding a monitor can keep the virtual thread mounted to its carrier.

02

Queueing versus pinning

ReentrantLock removes the observed monitor event, but a single critical section still bounds completed work.

03

Native residency

The JNI result is consistent with carrier occupation under stress, but its zero JFR count is not a direct pinning confirmation.

Thesis-ready wording

Conclusions

Supported: Under the tested Java 21 one-carrier condition, synchronized blocking generated monitor-pinning events; ReentrantLock avoided those observed events.
Supported: Long blocking JNI behaved differently from ordinary Java sleep across the repeated runtime matrix.
Not established: that Virtual Threads are faster in general, that Java 21 outperforms Java 24/25, or that zero JNI JFR events prove no carrier capture.
